# AGENTS.md — DailyPulse AI Developer & Agent Guide

> **Primary reference for AI agents and developers working on DailyPulse.**
> Read this first: stack, commands, folder layout, architecture rules and guardrails. The delivery process lives in [`WORKFLOW.md`](WORKFLOW.md).

---

## 1. Project Overview

**DailyPulse** is a minimalist, offline-first mood tracking app built with Flutter.

- **Tagline:** Track your emotions, understand patterns, maintain your well-being.
- **Core loop:** Log a mood (6 levels) → optional note → see it in History → see patterns in Insights.
- **Moods (index 0–5):** Frustrated, Terrible, Anxious, Neutral, Happy, Excited (emoji-based).
- **Data flow:** Hive CE (local, source of truth for the UI) → background sync → Cloud Firestore.
- **Auth:** Firebase Auth (email/password). Entries are always scoped by `userId`.
- **Themes:** Light **and** dark are both first-class and user-selectable (system / light / dark).
- **Single Flutter package:** `dailypulse` (no backend, no monorepo).

## 2. Tech Stack (from `pubspec.yaml`)

- **Framework:** Flutter, Dart `^3.11.3`, Material 3.
- **State management:** `signals_flutter` (`signal()`, `computed()`, `Watch` / `SignalBuilder`).
- **Routing:** `go_router` (`createAppRouter()` in `core/router/app_router.dart`, paths in `AppRoutes`).
- **Local storage:** `hive_ce` + `hive_ce_flutter` (hand-written `MoodEntryAdapter`, typeId `1`, box `mood_box`).
- **Remote:** `firebase_core`, `firebase_auth`, `cloud_firestore`; connectivity via `connectivity_plus`.
- **UI libs:** `google_fonts`, `flutter_svg`, `fl_chart`, `easy_date_timeline`.
- **Utilities:** `intl`, `uuid`, `logger` (`appLogger`), `path`, `path_provider`.
- **Tooling:** `flutter_lints`, `build_runner` (no generators in use today), `flutter_native_splash`, `flutter_launcher_icons`.
- **Not used (do not add):** Riverpod, Bloc, GetX, Provider, GetIt, ObjectBox (an old `fallback/objectbox` branch exists).

## 5. Architectural Conventions

### 5.1 Global
- **Language:** Code, comments, commit messages and PRs in English. When chatting with the user, reply in **Hinglish** (Roman Hindi + English tech terms).
- **Scope discipline:** Do only what was asked. No drive-by refactors, no speculative abstractions, no unsolicited tests.
- **Logging:** Use `appLogger` (`core/utils/app_logger.dart`). Never `print()`; no `debugPrint` for app logging.
- **DRY:** Shared helpers/formatters go in `lib/core/utils/` (e.g. `date_utils.dart`, `mood_utils.dart`). Never copy a helper across features.
- **Comments:** Short one-line docstrings where they add value. Don't narrate obvious code.

### 5.2 Feature layout & widgets (new features)
- **Feature-based MVVM**, under `lib/features/<feature>/`, only the layers that are needed:
  - `models/` plain data · `mappers/` transformations · `datasource/` raw Hive/Firestore access
  - `repository/` business logic + coordination · `services/` framework/system wrappers
  - `viewmodels/` signal-based state (`<name>_signal.dart`) · `views/` screens and widgets
  - Simple features (e.g. Splash) may have only `views/` + `viewmodels/`.
- **Class-based widgets only.** Never write helper methods returning widgets (`Widget _buildHeader()`); create a `StatelessWidget` / `StatefulWidget` class.
- **One widget per file** for non-trivial widgets (separate file, `snake_case.dart`).
- **Max 300 lines per UI file.** When you add code to a file already over 300 lines (`custom_button.dart`, `home_mood_screen.dart`, `insights_screen.dart`), extract the new part into its own widget file instead of growing it.

### 5.3 State management (signals_flutter)
- State lives in a `XSignal` class holding `signal<T>()` fields, `computed()` values and action methods.
- Existing pattern: one top-level instance per signal file (`final moodSignal = MoodSignal();`); the constructor takes an optional repository for substitution. Follow it.
- UI reads signals with `Watch((context) => ...)` (or `SignalBuilder`, already used in several screens — stay consistent within a file). Keep the reactive region as small as possible.
- **No new `ChangeNotifier` / `notifyListeners()`.** The only exception is `RouterRefreshStream`, required by go_router's `refreshListenable`.
- Never add Riverpod, Bloc, GetX, Provider or a service locator.
- Never `await` then use `BuildContext` without a `mounted` check.

### 5.4 Theming (light + dark are both required)
- Colors come from `Theme.of(context).colorScheme` (`context.colors`) or a **`ThemeExtension`** (`context.mood`, `.status`, `.cards`, `.gradients`, `.splash`, `.onboarding`).
- New semantic color needed → add it to the right `ThemeExtension` (or a new one registered in `context_extensions.dart` and both `light_theme.dart` / `dark_theme.dart`) with **both light and dark values**. Do not put one-off semantic colors in `AppColors`.
- No raw `Color(0xFF...)` / `Colors.xxx` in widgets. Legacy `AppConstants.moodColors*` and the `@Deprecated` `AppTheme` color statics must not be used in new code.
- Typography via `context.textTheme` / `AppTypography` (Google Fonts), not inline `TextStyle(fontSize: ...)` with magic numbers when a theme style fits.
- Always check a new screen in **both** themes.

### 5.5 Strings
- New or modified screens put user-facing copy in `lib/core/constant/strings/<feature>_strings.dart` (existing example: `onboarding_strings.dart`). Do not add new raw string literals to widgets. Existing screens are migrated gradually, only when touched for another reason.

### 5.6 Navigation
- All paths are constants in `AppRoutes`; routes are declared in `createAppRouter()`. New screens get a constant + a `GoRoute`; unauthenticated screens must be added to `AppRoutes.publicRoutes`.
- Navigate with `context.go` / `context.push`. No `Navigator.push(MaterialPageRoute(...))` for app screens.

### 5.7 Data layer: offline-first (critical)
- **Writes go to Hive first**, then `SyncService` pushes to Firestore in the background. UI never waits on the network and never reads Firestore directly.
- Firestore is accessed only through `FirestoreService`; local storage only through `HiveService`; screens go through signals → repository.
- An entry with `id == null` is **pending sync**. Preserve that invariant.
- **Hive schema safety:** `MoodEntryAdapter` is hand-written (typeId `1`, fields `0–5`). Never renumber, reuse or remove a field index; new fields get a new index and must tolerate `null` when reading old data. Never change `typeId` or the box name `mood_box`.
- **Every Firestore document carries `userId`** and every query filters on it; rules in `firestore.rules.template` allow per-user access only. Any new collection needs a matching rule added to the template.
- Handle offline/error states explicitly (empty, loading, error, offline) and log failures with `appLogger.e(..., error:, stackTrace:)`.

### 5.8 Modern Dart
Prefer `switch` expressions with `when` guards, records, pattern destructuring, `sealed` classes for states, `extension type` for typed wrappers, wildcard `_` for unused params, `const` constructors, and `?.`/`??` over `!`. Imports: Dart SDK → Flutter/packages → `package:dailypulse/...`.

### 5.9 Security
- `.env*`, service account JSON, `*.pem`, `*.key` are never committed, read or printed.
- `lib/firebase_options.dart`, `google-services.json`, `GoogleService-Info.plist` are git-ignored; never un-ignore or commit them.
- Never embed third-party secret keys in app code. If a feature needs one (e.g. an AI/LLM API), stop and propose a server-side proxy (e.g. Cloud Function) first.
- Never log mood notes, emails or tokens at `info` level or above.

## 6. Strict Prohibitions (Agents Must NEVER Do)

### Data & Backend
- ❌ Reset, wipe or migrate local/remote data destructively (`Hive.deleteFromDisk`, `deleteBox`, `firebase firestore:delete`) without the user's explicit, verbatim request.
- ❌ Change `MoodEntryAdapter` field indexes, `typeId` or the Hive box name.
- ❌ Read Firestore from widgets, or write to Firestore bypassing Hive + `SyncService`.
- ❌ Weaken `firestore.rules.template` (no open `allow read, write: if true`).
- ❌ Deploy rules or functions (`firebase deploy`) unprompted.

### Client Architecture
- ❌ New `ChangeNotifier` / `notifyListeners()`; Riverpod, Bloc, GetX, Provider, GetIt.
- ❌ Helper methods that return widgets; UI files over 300 lines; multiple large widgets in one file.
- ❌ Raw hex colors or ad-hoc semantic colors in widgets; code that only looks right in one theme.
- ❌ New hardcoded user-facing strings in widgets.
- ❌ `print()`; ignoring analyzer warnings with `// ignore:` to get to green.
- ❌ Duplicating helper logic across features (use `core/utils/`).
- ❌ Editing generated or platform files (`firebase_options.dart`, `pubspec.lock` by hand, `android/`, `ios/`, `build/`) unless the task is about them.

### Secrets
- ❌ Commit, read, print or log `.env*`, service account files, API keys, or tokens.

### Git & System
- ❌ `git reset --hard`, `git clean -f*`, `git checkout -- .`, `git push --force`, or `git stash`/discard of the user's uncommitted work without explicit permission.
- ❌ Commit or push without the Gate 2 approval in `WORKFLOW.md`.
- ❌ Run `release.bat` / `gh release create` unprompted.
- ❌ Add dependencies without telling the user which package, why, and what it replaces.

## 7. AI Subagents

Definitions live in `.agents/agents/<name>/agent.md`.

| Agent | Role | Use when |
|---|---|---|
| `dailypulse_frontend_builder` | Builds screens, widgets, signals, repositories and data-layer code in `lib/` following §5 | Any feature or UI work |
| `dailypulse_asset_generator` | Creates SVG/PNG assets and registers them in `pubspec.yaml`, matching the app palette in light and dark | New icons, illustrations, mood art |
| `dailypulse_pr_reviewer` | Audits against §5/§6, **auto-fixes** violations, runs `flutter analyze` + `flutter test`, issues a scorecard | Before commit / PR (Gate 2) |
| `code-reviewer` | **Read-only** review of branch vs `main`: correctness → security/data safety → performance → conventions | Neutral second opinion |
| `pr-describer` | Read-only. Conventional-Commit PR title + description from `git diff main...HEAD` | Ready to open a PR |
| `diff-explainer` | Read-only. Plain-language walkthrough of any diff | Understanding a change |
